# Agent 任务线程接收状态与交付 PRD

## 背景

AgentBean 的频道消息、讨论串和任务已经统一在 Team 内协作。用户希望 Agent 面对“任务式消息”时既能及时呈现接收状态，又不把 Server 协调状态伪装成 Agent 发言或把主频道刷成多段过程日志；真正的 Agent 回复、结果和状态流转应该落在同一个任务线程里。

本 PRD 定义 Agent 处理任务或讨论串式消息的默认产品语义。

## 目标

- 让用户在发送可执行任务后立即知道任务正在发送、已被 Agent 接收或正在执行。
- 区分普通问答和需要执行/产出的任务，避免所有消息都被转成任务。
- 保持主频道克制：短确认、必要进度、最终交付都围绕任务线程组织。
- Agent 交付后默认进入 `in_review`，等待用户审核；只有用户明确确认后才进入 `done`。

## 非目标

- 不引入新的任务状态枚举。
- 不让普通能力咨询、闲聊、寒暄自动变成任务。
- 不在本期实现复杂多步进度规划、自动阻塞诊断或用户确认语义的自然语言解析。

## 用户故事

1. 作为用户，我发送“请总结附件并产出报告”后，希望原消息旁立即显示目标 Agent 与请求摘要，避免我以为没人响应。
2. 作为用户，我问“你能做什么”或“什么样的消息算任务”时，希望 Agent 直接回答，不创建任务、不认领。
3. 作为用户，我希望 Agent 的正式结果、附件、文件链接或验证说明出现在同一讨论串中，方便追踪上下文。
4. 作为用户，我希望 Agent 交付后任务进入待审核，而不是直接被系统标成已完成。

## 产品规则

### 任务判定

消息满足以下条件时才进入任务处理流程：

- 明确要求 Agent 执行、产出、处理附件、处理代码、查资料、生成文件、跑命令或验证结果。
- 或用户显式把消息标记为任务。
- 普通问答、能力咨询、寒暄、纯讨论不自动认领。

### 接收状态

任务被派发后，Web 在用户原消息旁根据权威 Dispatch 状态展示请求感知的短状态：

- `queued` / `sent`：`正在发送给 OpenSNS：「整理技能清单并输出 Markdown 文件」`
- `accepted` / `running`：`OpenSNS 已接收，正在处理：「整理技能清单并输出 Markdown 文件」`

状态由 Server Dispatch 事实驱动，不创建 `senderKind=agent` 的 Message，也不计入 Thread 回复数。只有 Agent 实际返回的内容才显示为 Agent 消息。历史 `meta.kind=task-claim-confirmed` 只作为兼容数据保留，不进入聊天视图。

### 执行与进度

- Agent 后续正式执行下载附件、查资料、写内容、生成文件、跑命令或验证结果。
- 同一次 Agent 执行可在开始实际工作后，通过 Daemon 提供的受管活动文件写入一条用户可见计划或进度；正文必须由 Agent 自己生成，Daemon 和 Server 只校验、转发、去重。
- 当前协议每次 Dispatch 最多一条，使用 `schemaVersion=1`、`sequence=1` 和稳定 `updateId`；Server 持久化为 `meta.kind=dispatch-agent-message` 的真实 Agent Message。
- 简单任务可以不写活动文件，直接交付；未写、格式非法、运行时不支持或传输失败时，Web 继续显示上面的结构化 Dispatch 状态。
- 真实 Agent 动态出现在界面后，Web 收起同一 Dispatch 的“正在处理”兜底，避免重复表达。

### 交付与状态

- Agent 正式结果仍作为 Agent 消息发回原任务线程。
- 派发成功时任务进入 `in_progress`。
- Agent 成功交付后任务进入 `in_review`。
- 用户明确确认 OK 后，任务才应被移动到 `done`。
- 失败或阻塞时不自动 `done`，应保留可继续处理的状态。

## 验收标准

- Task-like channel message 会创建任务线程并分配给被派发 Agent，但不生成 Server 代写的 Agent 接单消息。
- 接收状态通过 `message:dispatch-status` 和消息读路径中的 Dispatch 投影驱动，并包含目标 Agent 与当前请求摘要。
- Agent 在同一次执行中写入合法的首条计划时，Daemon 通过 `dispatch:message` 上报，Server 幂等归档为 Agent Message；重复上报不新增消息，冲突正文被拒绝。
- 已出现真实 Agent 动态时，不再同时显示同一 Dispatch 的进行中结构化状态；没有真实动态时状态仍可刷新恢复。
- Agent 成功返回结果后，结果消息进入同一线程，任务状态为 `in_review`。
- 历史 `task-claim-confirmed` 消息不进入频道主线、Thread 回复与回复计数。
- 普通问答仍只是普通消息/普通 dispatch，不产生任务接收状态。
- SQLite 持久化中的任务状态与内存 use case 返回值一致。

## 风险与边界

- 当前任务判定仍是轻量启发式，后续可引入更明确的 intent classifier 或用户可配置规则。
- 当前请求摘要采用确定性裁剪，不额外调用模型；可选的一句话计划也来自同一次真实 Agent 执行，不引入第二次模型调用。
- Hermes 0.20.5 的 `-z` 模式只在结束时输出最终正文，因此不能把 stdout 首行当成可靠计划；受管活动文件是独立的显式来源。Agent 未遵守可选协议时不伪造消息。
- 本期只定义“交付后待审核”；“用户说 OK 自动 done”的自然语言确认仍留给后续切片。
