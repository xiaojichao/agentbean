# AgentBean 项目任务与文件管理架构设计

- 日期：2026-07-17
- 目的：说明产品模型、领域边界、关键流程和验收标准，供实现同学据此拆解开发任务。
- 范围：频道项目化、阶段任务、项目产物、文件版本、最终版、多文件选择、人审与 Agent 交接。

---

## 1. 结论

首版项目管理不新增一个脱离频道的顶层 `Project` 系统。一个频道就是一个项目空间，频道继续承载成员、权限、消息、任务线程、Agent 可见性和文件可见性。

核心决策：

- **频道即项目**：频道天然具备项目能力，不需要用户手动开启“项目模式”，也不新增项目容器。
- **阶段不是状态列**：剧本、服装、分镜、审核是项目阶段，应该绑定到任务图节点；不要把它们塞进 `TaskStatus`。
- **文件不是普通附件**：聊天附件只是文件出现的位置；项目产物需要有类型、版本、审核态、来源和最终版指针。
- **最终版不是文件名或标签**：最终版必须是 Server 持久化的版本指针，可追溯、可审计。
- **聊天不是事实源**：聊天用于协作和触发操作；项目阶段、审核、版本和最终版都必须由 Server 写入事实。
- **负责人不是手填 Agent 下拉**：任务页展示当前责任焦点，但 Agent 执行必须由讨论串中的 `@智能体 + 文件引用 + 指令` 显式触发。
- **默认引用最新 Server 修订**：`@文件包` 和“整包引用当前版本”默认读取包内成员各自的 `currentVersionId`；引用最终版必须显式选择。
- **任务状态不是人工下拉**：`TaskStatus` 是 Server 生命周期投影，用户通过具名动作推进任务，不能在任务页自由拖动或选择状态。
- **首版任务由讨论串触发**：任务列表不是新建任务入口；用户在讨论串发送 `@智能体 + 指令 + 文件引用` 后，Server 创建 Task/Invocation 并进入执行事实。
- **文件包不是审核对象**：输出包只是冻结交付容器和批量入口；审核事实必须落到包内每个文件版本。
- **文件审核不等于任务验收**：文件版本审核、最终版设置和 Task 交付验收是三类独立事实。
- **权限语义分离，默认体验可同人**：文件审核权决定文件版本是否可用，Task 交付验收权决定任务目标是否完成。首版可以默认让任务发起人或项目负责人同时拥有两类动作，但系统不能用其中一类权限或事实推导另一类。

一句话定义：

> 频道是项目空间，阶段是有依赖和审核规则的任务节点，文件是可版本化、可审核、可设最终版的项目产物，Agent 交付由文件版本审核和 Task 交付验收共同收口。

## 2. 用户流程

目标用户流程如下：

1. 真人负责人创建或进入一个频道，这个频道就是项目协作空间。
2. 项目里有真人负责人、真人审核者，以及多个 Agent。
3. 不同 Agent 负责不同阶段，例如编剧、服装、分镜。
4. 编剧 Agent 先生成剧本、提示词、参考图等多个文件。
5. 真人审核这些文件，可能通过、拒绝、要求修改，也可能选定最终版。
6. 文件版本审核通过且当前交付完成验收后，后续 Agent 基于已通过或最终版文件继续工作。
7. 如果一条消息里有多个文件，用户必须能整包引用、单个引用或多选引用，发起修改、审核、交给 Agent 或设为最终版。

这个流程的关键不是“任务列表更好看”，而是让项目负责人始终知道：

- 当前项目有哪些阶段。
- 每个阶段由谁负责。
- 哪些阶段正在执行、等待审核、已经完成或被阻塞。
- 每个阶段产出了哪些文件。
- 哪些文件是草稿、候选、已通过、被拒绝或最终版。
- 后续 Agent 使用的是哪一版输入。

## 3. 目标与非目标

### 目标

- 在任务页清楚展示已有执行事实对应的项目阶段、当前责任焦点、执行 Agent、建议审核人、实际审核人、状态、阻塞点和交付物。
- 支持“Agent 产出 -> 真人审核 -> 后续 Agent 继续”的顺序推进。
- 支持 Agent 输出物按脚本、提示词、图片、分镜、服装参考等类别归档。
- 支持多文件消息中的精确选择和修改指派。
- 支持可追溯的最终版选择。
- 支持 Agent-managed task 的交付审核：逐文件版本审核、批量审核文件、验收或退回当前 delivery。
- 复用现有 `Channel`、`TaskStatus`、Task DAG、`ManagementRun`、`AgentInvocation`、`Artifact` 和 `WorkspaceRun`。

### 非目标

- 首版不做跨频道项目。
- 首版不做甘特图、预算、人力负载、资源排期。
- 不用业务阶段扩展 `TaskStatus`。
- 不要求所有外部 Agent 直接理解项目数据库。
- 不把普通人工任务工作流做成本次首版重点；存量普通任务只保留最小查看、关闭、删除或从讨论串转入 Agent 流程能力。
- 不在任务列表提供“新建任务”主入口，也不把未发送的想法、草稿或普通描述自动提升为 Task。
- 不允许用户通过看板拖拽、下拉或通用更新接口直接写入 `TaskStatus`。
- 不创建 package-level review version；文件包批量审核必须拆成多个文件版本审核事实。
- 不把文件审核通过、设为最终版或文件包聚合态自动等同于 Task 完成。
- 不用文件名、标签或目录名判断最终版。
- 不允许外部 Agent 直接修改项目事实；外部 Agent 只能产出结果或 proposal，由 Manager/Server 校验后写入事实。

## 4. 核心模型

本文只定义职责和关系，不把字段写死成最终 DTO 或表结构。实现同学可以按现有代码风格调整命名和拆分，但语义边界不要改变。

### 4.1 ChannelProjectProfile

频道项目画像是内部配置和投影，不是用户可感知的“模式开关”，也不新增独立的项目生命周期状态。所有频道都天然可以承载项目；当频道出现项目负责人、阶段、审核规则或项目产物时，Server 可以按需创建或更新这类记录。频道是否结束继续由 `Channel archive` 表达；进行中、暂停等运营视图从阶段、任务和审核事实聚合，不写入独立的 Project 状态。

它负责表达：

- 项目总负责人是谁。
- 默认审核者是谁。
- 是否使用某个阶段模板。
- 默认输出归档策略是什么。

它不替代 `Channel`，也不决定频道是不是项目。频道名称、成员、权限、可见性、归档状态仍由 `Channel` 管理。

### 4.2 ProjectStage

项目阶段，例如剧本、服装、分镜、总审。

它负责表达：

- 阶段目标是什么。
- 阶段绑定哪个任务或任务线程。
- 阶段当前责任焦点是什么，例如未开始、某个 Agent 执行中、等待人审或已完成。
- 阶段是否需要审核，是否有建议审核人。
- 阶段期望产出哪些类型的文件。

阶段状态默认从绑定任务、当前 delivery 和产物审核状态聚合，不新增业务状态枚举。`todo`、`in_progress`、`in_review`、`done`、`cancelled`、`closed` 仍是基础任务生命周期投影，只能由 Server 具名命令推进。

### 4.3 ProjectStageEdge

阶段之间的依赖关系。

它负责表达：

- 哪个阶段完成后才能启动后续阶段。
- 哪个阶段的产物会作为后续阶段上下文。
- 哪些产物是后续阶段必需输入。

典型关系：

- 剧本通过后，服装阶段才可以开始。
- 剧本最终版作为分镜 Agent 的输入。
- 分镜和服装都完成后，进入总审。

### 4.4 ProjectArtifactCollection

项目产物集合，表示一个逻辑交付物，例如“第 1 集剧本”“女主服装参考”“分镜图组”。

它负责表达：

- 这个产物属于哪个项目、阶段和任务。
- 产物类型是什么。
- 当前版本是哪一个。
- 最终版是哪一个。
- 当前审核状态是什么。

集合不保存文件内容。文件内容仍由已有 `Artifact` 管理。

### 4.5 ProjectArtifactVersion

项目产物版本，绑定一个已有 `Artifact`。

它负责表达：

- 这是某个产物集合的第几个版本。
- 文件来自哪条消息、哪次 Workspace Run、哪次 Agent invocation、哪个任务。
- 这个版本是草稿、候选、待审核、已通过、已拒绝、最终版还是归档。
- 它从哪些旧版本或输入演进而来。

`Artifact` 是文件事实；`ProjectArtifactVersion` 是项目语义事实。一个文件可以只是普通附件，也可以被提升为项目产物版本。

### 4.6 ArtifactReview

审核记录。Agent 交付审核的最小对象是具体产物版本。阶段、任务和文件包可以展示聚合审核覆盖，但不能用一条聚合审核替代包内文件版本审核。

它负责表达：

- 谁审核了什么。
- 审核结论是通过、拒绝还是要求修改。
- 审核意见对应哪条消息。
- 审核依据引用了哪些文件版本。
- 实际审核动作由谁执行。首版即使任务里预设了建议审核人，审核归属也必须落到真正点击审核按钮的人。

审核通过不等于最终版，也不等于 Task 完成。最终版选择是单独动作，Task 完成必须走交付验收。

### 4.7 ArtifactReference

聊天、任务和 Agent invocation 中使用的稳定文件引用。

它负责表达：

- 用户选中的到底是哪一个文件或哪一个版本。
- 这个引用在当前消息里如何展示，例如 `F3`、`IMG-02`、`SCRIPT-v4`。
- 这个引用来自哪条消息和消息内第几个文件。

消息内序号只能帮助用户理解当前上下文，不能作为长期身份。长期身份必须依赖 `artifactId` 或 `artifactVersionId`。

### 4.8 OutputPackage

输出包表示一次 Agent invocation 交付出来的一组项目产物，例如 `PKG-042 剧本输出包`。

它负责表达：

- 这次交付来自哪个 Agent、哪次 Workspace Run、哪条消息和哪个任务。
- 创建时包含哪些产物集合或产物版本。
- 包内文件在当前讨论串中的短编号，例如 `F1`、`F2`、`IMG`。
- 整包引用 current 或 final 时，Server 应如何把包成员投影到具体版本。

输出包不是文件夹，也不是独立审核对象。它的成员列表创建后默认冻结，不能因为后续新增文件而静默变化；但包内既有成员各自的 `currentVersionId` 可以随着人工编辑或 Agent 修订更新。输出包只展示成员聚合审核态和可用批量动作；真正的审核记录仍写到每个成员对应的 `ProjectArtifactVersion`。

## 5. 关键规则

### 5.1 阶段推进

推荐默认流程：

1. 项目负责人在频道中创建阶段或指定项目负责人，Server 按需补齐项目画像。
2. Server 根据模板或手动配置生成阶段。
3. 用户在讨论串中通过 `@智能体 + 文件引用 + 指令` 触发某个 Agent 执行，Server 创建 invocation/claim 后绑定任务进入 `in_progress`。
4. Agent 交付文件后，Server 形成冻结输出包和成员文件版本，Task delivery 进入 `in_review`，相关成员版本进入待审核。
5. 真人从任务卡片、文件包成员行或文件页版本行打开预览/编辑浮窗，在看到具体内容后逐文件审核；批量入口可以为多个成员版本写入同类审核记录，但确认时仍必须列出受影响版本。
6. 文件审核覆盖满足后，合法验收人通过交付验收命令让 Task 进入 `done`；文件审核通过本身不自动完成 Task。
7. 审核者可以把某个已通过版本设为最终版，或在“通过”确认面板中勾选“同时设为最终版”；最终版仍是文件集合指针，不是 Task 状态。
8. 后续阶段启动时，Server 按阶段输入规则把已通过或最终版产物作为上下文传给下一个 Agent。

如果审核要求修改或拒绝，系统写入被退回的具体版本、审核意见和 Task delivery 退回事实，Task 从 `in_review` 回到可继续执行状态并产生新的 revision/attempt。系统不自动重跑原 Agent；后续修改必须由用户在讨论串中显式选择 Agent，并引用被退回版本和审核意见，不能只靠自然语言说“改一下刚才那个”。

任务页不提供把 Agent 直接选为负责人的普通下拉，也不提供自由修改 `TaskStatus` 的拖拽、下拉或五状态按钮。首版任务列表不是创建入口；新的 Agent-managed task 由讨论串中的 `@智能体 + 文件引用 + 指令` 触发，用户发送后 Server 才创建 Task/Invocation，任务负责人或当前责任焦点才投影为该 Agent。审核退回后的“让原智能体修改”和“换一个智能体处理”也只把用户带回讨论串并预填上下文，不在任务列表里生成待办空壳。

任务页中的“负责人”不是传统项目管理里的永久 assignee，而是当前责任焦点：

- 执行中：显示当前 Agent。
- 待审核：焦点转为“审核交付”，展示文件审核覆盖和交付验收门槛，而不是继续暗示 Agent 还在负责。
- 已完成：展示最终执行方，并在详情中保留完整执行链。

执行中的任务可以提供“查看执行进度”和“打开讨论串”两个动作。“查看执行进度”只读展示当前 Agent run、WorkspaceRun、日志、最近事件或中间输出；“打开讨论串”只把用户带回原上下文，不改变当前 Agent 正在使用的冻结输入。用户在讨论串补充普通消息默认只是讨论记录；只有重新发送明确的 `@智能体 + 指令 + 文件引用`，才会形成后续执行、修订或重新处理。

`done`、`cancelled` 和 `closed` 是终态，不能回退到 `todo`、`in_progress` 或 `in_review`。如果已完成、已取消或已关闭后还要继续，应创建带 lineage 的 follow-up、continuation 或 replacement task，并引用原 Task 和相关文件版本。

### 5.2 文件归档

Agent 仍然把文件写入现有 `AGENTBEAN_OUTPUT_DIR`。当频道、阶段或单次 invocation 配置了输出分类策略时，可以下发这些约定目录，例如：

```text
outputs/
  scripts/
  prompts/
  images/
  storyboards/
```

Device 不需要理解项目数据库，只要按约定目录输出文件。Artifact collector 上传后，由 Server 根据输出路径、mime type、阶段期望和 invocation context 判断产物类型，并创建或更新项目产物集合和版本。

### 5.3 最终版

最终版必须满足：

- 属于当前频道的项目产物集合。
- 属于可最终化的产物集合。
- 通常应来自已通过版本。
- 设置动作由有权限的人类触发，或由 Manager 代表明确的人类确认触发。

同一产物集合同时只能有一个最终版。新最终版产生时，旧最终版不删除，应保留历史并回到已通过或被取代状态。

`设为最终版` 只能作用于已通过版本。若当前版本还在待审核，但用户想一步完成，UI 应在“通过”确认面板中提供“同时设为最终版”勾选项，并在一次事务中同时写入审核通过记录和 `finalVersionId`。

任务或阶段完成不强制依赖最终版。默认规则是：核心产物审核通过后才可能验收当前 delivery；最终版表示定稿或交付指针。后续阶段如果要求稳定输入，可以单独要求引用最终版。

最终版不能只靠这些方式表达：

- 文件名含 `final`。
- 标签含“最终版”。
- 放在某个 `final/` 目录。
- 聊天里用户说“这个就是最终版”但 Server 没有写入事实。

### 5.4 `pathKind` 不承载业务语义

现有 `Artifact.pathKind` 继续只表达文件来源，例如 `upload`、`workspace`、`generated`。

项目产物类型必须放在项目产物元数据中，例如 `script`、`prompt`、`image`、`storyboard`、`costume_reference`。

不要把“文件从哪里来”和“文件在项目里代表什么”混在一个字段里。

### 5.5 多文件选择

当一条消息包含多个文件时，UI 可以展示短编号：

- `F1`、`F2`、`F3`：当前消息内的编号。
- `IMG-02`、`SCRIPT-v4`：更稳定的项目语义编号。

用户点击或选择文件后，发送消息、审核、修改、交接时必须携带稳定引用，例如 `artifactVersionId`。Agent invocation 不应该接收“第 3 个文件”这种模糊输入。

如果用户说“改第 3 个”，系统可以在当前焦点消息内解析并插入引用 chip。如果当前上下文里有多个可能的“第 3 个”，必须让用户选择，不能猜。

讨论串中文件包卡片应同时保留三种引用入口：

- **整包引用**：一键插入 `@PKG-042 current`，默认读取包内每个成员各自的 `currentVersionId`。
- **单个引用**：在文件行内插入某个文件的稳定引用 chip。
- **多选引用**：进入当前包卡的选择状态，勾选多个文件后插入多个独立稳定 chip，不自动生成新包。

`F1/F2/IMG` 只在当前文件包或当前讨论焦点中可见。发送消息时必须转换为 `artifactVersionId` 或 `artifactCollectionId + versionPolicy`。如果讨论串里有多个包都包含 `F1`，UI 必须弹出选择器。

输出包成员列表创建后冻结。后续人工编辑或 Agent 修订只更新成员各自的 `currentVersionId`；新文件不会自动加入旧包。首版不做自定义包或另存为包。

`@PKG-042` 默认表示引用当前包，即包内成员各自的最新 Server 修订。若用户选择“引用最终版包”，包内每个成员都必须存在 `finalVersionId`；只要有成员缺失 final，就应阻止并提示缺失项，让用户去设置最终版或改为引用当前版，不能静默混用 `final + current`。

被拒绝版本可以被显式引用来“基于此修改或重做”，但不能作为整包默认输入或后续正式输入。如果某个包成员的 current 版本处于 `rejected`，整包引用应提示并要求用户选择可用版本。

`changes_requested` 版本仍然可以是 `currentVersionId`，因为 current 表示最新 Server 修订，不表示可用。它不能作为下游默认正式输入，只能作为继续修改的基础。

## 6. 人审与 Agent 交接

阶段可以配置审核策略：

- `none`：交付后可自动推进。
- `human`：必须真人审核后推进。
- `manager`：Manager 可根据验收标准和 evidence 判定，必要时转真人。

`manager` 不表示 Manager 可以代替人类执行文件版本审核、最终版设置或主观交付验收。它只能在客观 evidence 足够时推进低风险判断，或把需要主观判断、创意取舍、最终定稿和交付验收的环节转给人类。

创意类项目里，剧本、分镜、最终合成等阶段默认应该走真人审核。

审核、最终化与交付验收入口必须来自 Server projection 的 `availableActions`，客户端不能根据角色、本地缓存或按钮可见性自行推导权限。当前语义下，文件版本审核与最终化由 Team owner/admin、项目负责人或该阶段审核者等具备项目决定权的人类执行；Task 交付验收由当前 Task 的合法验收人执行。两类权限可以默认落到同一个人身上，尤其是人少、Agent 多的频道；但它们在模型和审计上仍是不同 authority，不能因为能审核文件就自动拥有任务验收权，也不能因为能验收任务就自动批准文件版本。Agent 和 PI Manager 不能直接替代人类审核。任务里可以预设“建议审核人”，也可以为空；建议审核人只是提示或默认分配，不等于最终审核归属。最终审核归属永远以实际点击审核动作的人为准，并写入 `ArtifactReview.actorId` 或对应交付验收事实。

Agent-managed task 的 `in_review` 表示当前 delivery 等待人类处理，不是单纯的文件状态。界面必须同时展示：

- 文件审核覆盖：包内每个成员版本的待审核、已通过、要求修改或已拒绝状态。
- 交付验收门槛：当前 delivery 是否已经具备被验收为 `done` 的条件。

文件全部通过后，Task 可以显示“文件审核已完成，等待交付验收”。如果验收规则简单，UI 可以提供“全部通过并验收交付”组合入口，但落库时仍必须分别写入多条文件版本审核记录和一条 Task delivery acceptance。只要有成员是 `changes_requested` 或 `rejected`，就不能同时验收交付。

输出包可以提供“一键审核”入口，但它只是批量操作。面向用户的按钮建议使用“批量审核文件”“验收本次交付”“全部通过”“全部通过并验收本次交付”“全部要求修改”“全部拒绝”等产品文案，避免暴露 `Task delivery acceptance`、package member、F1 等实现术语。确认面板必须列出将影响的文件版本，并允许统一意见。需要不同结论时，用户应逐项处理或进入逐项调整。批量操作遇到 stale、无权限或不属于当前 delivery 的文件时必须明确提示，不能静默跳过。

后续 Agent 的输入由 Server 组装，不靠复制完整聊天记录。输入应包含：

- 上游阶段摘要。
- 上游阶段已通过或最终版产物。
- 审核意见。
- 当前阶段目标和验收标准。
- 必需附件和文件引用。
- 必要的线程消息片段。

沿用多 Agent 交接设计的安全边界：

- 外部 Agent 可以提出交接 proposal。
- Manager/Server 校验阶段依赖、审核状态、目标 Agent 可见性和权限。
- 校验通过后才创建正式 handoff 或后续 invocation。
- 目标 Agent accepted/running 后，当前责任焦点才投影为该 Agent。
- 目标 Agent 未接收时，任务仍显示未开始或等待讨论串指令，不把 Agent 写成已负责。

任务详情应保留执行链，例如 `@剧本Agent -> derrick 手改 -> @润色Agent -> derrick 审核通过`。任务卡片只显示当前责任焦点，不要求在卡片上塞下完整历史。

审核退回后系统不自动重跑 Agent。`要求修改` 和 `拒绝` 不应只是孤立状态按钮，而应进入同一个退回流程：用户必须填写审核意见，并选择“让原智能体修改”或“换一个智能体处理”。确认退回后，UI 只预填讨论串中的 `@智能体 + 被退回文件版本 + 审核意见 + 原任务上下文`；用户发送后 Server 才创建新的 invocation/claim 并冻结输入版本。

## 7. 产品界面期望

### 7.1 项目总览

任务页进入频道时，不需要用户先切换“项目模式”。如果该频道已有阶段、项目产物或项目负责人，默认展示阶段总览；如果还没有这些项目数据，则可以保持普通任务视图，并引导用户回到讨论串发起第一个 Agent 请求。

阶段卡片应让项目负责人一眼看到：

- 阶段名称。
- 当前状态。
- 当前责任焦点。
- 建议审核人和实际审核人。
- 前置依赖是否满足。
- 产物数量和最终版数量。
- 当前阻塞原因。

普通任务看板仍可保留，作为只读状态视图或执行者视图。首版主列表只展示已经形成执行事实的 `进行中`、等待人处理的 `待审核` 和已验收的 `已完成`；`todo`、`cancelled`、`closed` 可作为后端状态或历史筛选存在，但不做常驻主列。看板列和列表状态下拉不得作为人工改写 `TaskStatus` 的入口；列位置由 Server 生命周期事实决定。每个状态下只展示合法具名动作，例如 `in_progress` 的“查看执行进度/打开讨论串”、`in_review` 的“查看交付文件/审核交付文件/打开讨论串”、`done` 的“查看历史/创建后续任务”。

待审核任务卡片是列表入口，不承载完整文件审核操作。卡片只展示本次交付摘要、文件审核覆盖数量、交付验收状态和“查看交付文件 / 审核交付文件 / 打开讨论串”等入口。“查看交付文件”跳到文件页的输出包概览，用于查看、预览、引用和使用交付文件；“审核交付文件”直接打开预览/编辑浮窗，并选中本次输出包中第一个需要处理的文件版本。文件级审核按钮必须明确绑定到当前预览的文件版本；没有明确预览对象时，应隐藏或禁用文件级审核按钮，并提示先打开要审核的文件。

### 7.2 阶段详情

点击阶段后，应看到：

- 阶段目标和验收标准。
- 绑定任务线程。
- 当前责任焦点、建议审核人和实际审核人。
- 上游输入产物。
- 当前阶段产物集合和版本。
- 当前 delivery 和输出包成员。
- 可预览、可选择的交付文件列表，以及当前预览的文件版本。
- 文件审核覆盖和交付验收门槛。
- Agent 调用记录和 Workspace Run。
- 审核历史。
- 保存新版本、逐文件通过、退回修改、批量审核文件、验收本次交付、回到讨论串继续等动作。逐文件审核动作只能作用于当前预览的交付文件版本；按钮文案应面向用户，不直接显示 `F1`、`Task delivery acceptance` 或 package member 等实现术语。底部主按钮不应把“要求修改”和“拒绝”并列成两个无后续的终点按钮，而应统一为“退回修改...”入口；退回面板里再选择要求修改或拒绝，并填写意见。

任务列表卡片、文件页和预览浮窗要分层：任务卡片用于扫状态和进入处理，只展示摘要与入口；文件页默认是文件包和文件的查看/使用空间，按输出包展示过程文件、最终版、审核态、来源、预览和引用入口；预览/编辑浮窗才是逐文件审核的主工作面，因为审核者必须看到文件内容和版本后才能保存新版本、通过或退回修改。不要在待审核任务卡片里直接铺开完整审核操作，也不要让文件页变成审核台而失去文件库用途。

### 7.3 文件库

项目文件库应按逻辑产物集合组织，而不是按聊天消息附件堆叠。

文件库左侧可以展示产物集合或输出包列表，但它不是普通文件夹树。一个集合可以表示同一逻辑交付物的多个版本，例如“角色设定集合”；一个输出包可以表示一次 Agent 交付的一组文件，例如 `PKG-042 剧本输出包`。输出包摘要中可以展示 `F1 v4 / F2 v3 / F3 v2` 这类短编号和版本，帮助用户识别当前讨论串内的文件，但长期身份仍是 Server 中的 collection 和 version。

文件库首版保持轻量卡片结构，不重构成复杂文件系统。左侧卡片可以混排：

- `输出包`：一次 Agent 输出的一组文件，成员冻结。
- `文件集合`：一个长期文件或逻辑文件组，展示版本演进。
- `等待上游`：后续阶段尚无产物的占位状态。

这些卡片默认按最近活跃排序，最近有 Agent 输出、人工编辑、审核、设 final 的内容排前面；可提供 `全部 / 待审核 / 有 final / Agent 输出` 等轻量筛选。UI 不要求用户理解底层的 `ProjectArtifactCollection` 与 `OutputPackage` 差异，底层语义留给实现和调试。

当用户直接进入文件页或从任务点击“查看交付文件”时，文件页应优先展示输出包概览：包内过程文件、最终版状态、审核状态、来源、预览、引用和历史。文件页右侧同一时间只展示左侧当前选中对象的详情：选中输出包时展示包内文件；选中文件集合时展示该集合版本历史和最终版信息；不要在一个详情页里同时铺输出包详情和全局文件表。用户需要继续处理时，通过文件行或“审核待审文件”打开预览/编辑浮窗。预览浮窗左侧展示本次输出包成员列表和审核状态，中间展示当前文件内容，底部展示只作用于当前文件版本的审核动作。输出包仍不是审核对象；所有通过、要求修改、拒绝和设最终版动作都落在具体文件版本上。只有文件审核门槛满足后，“验收本次交付”才可用，并写入独立的 Task 交付验收事实。

每个集合应展示：

- 产物名称和类型。
- 所属阶段。
- 当前版本。
- 最终版。
- 审核状态。
- 历史版本。
- 所属输出包成员关系。
- 来源消息、任务或 Workspace Run。

### 7.4 聊天与讨论串

主聊天区展示话题入口，不直接承载连续回复和完整文件包操作。点击话题后，右侧讨论串展示该话题内的请求、回复、Agent 输出文件包和引用输入框。

讨论串是当前话题的主要操作容器，首版可以作为右侧栏展示，并应支持向左拖宽；后续可以演进为最大化讨论串视图。无论是右侧栏还是最大化视图，同一套文件包卡片、预览编辑、引用输入和审核入口语义不变。

讨论串中的文件包应支持：

- 显示项目语义编号和版本。
- 展示包内文件的短编号、文件名、当前版本、审核态和来源摘要。
- 预览或编辑具体 Markdown 文件。
- 在每个成员行打开文件预览，并在预览浮窗中触发单文件版本审核。
- 批量审核包内成员版本；确认面板必须列出目标版本，不能生成包级审核。
- 整包引用当前版本。
- 多选引用包内部分文件。
- 显式引用最终版包。
- 打开文件页对应输出包概览，或直接打开预览浮窗处理待审文件。
- 在讨论串输入框中通过 `@文件`、`@文件包` 和 `@智能体` 完成精确引用与后续协作。

聊天负责触发操作，操作结果必须落回项目事实模型。

## 8. 交互与状态契约

本节是实现同学对照 UI 原型时的约束说明。原型中的按钮和标签只是展示形态，真正可依赖的是下面这些状态写入规则。

### 8.0 按钮与交互说明

首版原型中的按钮按界面位置分为四组。实现时按钮是否可见、可点、置灰都必须来自 Server 返回的 `availableActions`；客户端不能只根据当前 tab、卡片状态或角色名称自行推导权限。

任务页按钮：

- **查看执行进度**：只读打开当前 Agent run / WorkspaceRun / 日志 / 中间输出进度视图。它不改变任务状态，不修改 Agent 当前冻结输入，也不把普通消息追加为新执行。
- **打开讨论串**：定位到创建该任务的原话题讨论串。它只是回到上下文，不写入审核、版本、最终版或 Task 状态。
- **查看交付文件**：切到文件页并选中当前 delivery 对应的输出包，展示包内文件、版本、来源、审核态、最终版和引用入口。它不进入审核结论，也不打开退回流程。
- **审核交付文件**：打开预览/编辑浮窗，并默认选中本次输出包中第一个需要处理的文件版本。用户在看到文件内容后，才能执行保存新版本、通过或退回修改；通过确认面板可以选择“同时设为最终版”。

文件页按钮：

- **多选引用**：让用户在当前文件组内选择多个文件版本，并在讨论串输入框中插入多个稳定引用 chip。它不创建新包，也不改变文件状态。
- **引用当前包**：引用当前输出包的 current projection，即包内每个成员各自最新的 Server 修订。若成员 current 处于拒绝或要求修改状态，应提示用户确认或改用可用版本。
- **引用最终版包**：引用当前输出包的 final projection。包内所有必需成员都必须有最终版；缺失最终版时应阻止并列出缺失文件。
- **引用已选文件**：只引用用户在当前详情中选择的文件版本，提交给后端时必须是稳定 `artifactVersionId`，不能只提交 F1/F2 或行号。
- **审核待审文件**：打开预览/编辑浮窗，并定位到当前输出包的待审核或待处理文件；审核动作仍在浮窗中完成。
- **预览/审核**：打开当前文件版本的预览/编辑浮窗。该按钮只选择审核对象，不直接写入审核结论。
- **预览/处理**：打开当前已经要求修改或被退回的文件版本，展示内容和退回意见，并允许用户回到讨论串继续处理。
- **历史**：打开当前文件集合或文件版本的历史记录，展示来源、旧版本、审核记录和最终版变更。它不改变当前版或最终版。

讨论串文件包按钮：

- **预览**：打开当前文件或输出包中默认文件的预览浮窗，只读或可编辑取决于文件类型和权限。
- **逐个预览审核 / 审核交付文件**：打开预览/编辑浮窗处理本次输出包的待审文件。它不在讨论串卡片内直接通过或拒绝文件。
- **引用已选 N 个**：把当前勾选的文件版本插入讨论串输入框，后续是否触发 Agent 取决于用户是否发送 `@智能体 + 指令`。
- **基于此修改**：把当前文件版本作为上下文引用到讨论串输入框，通常配合 `@智能体` 或人工说明继续修改。
- **验收本次交付**：Task 交付验收动作。只有当前 delivery 的必需文件版本满足审核门槛时才可用；它写入 Task delivery acceptance，让任务进入完成态或验收结果态，不替代文件版本审核。

预览/编辑浮窗按钮：

- **当前文件 / 切换查看**：在左侧输出包成员列表中切换当前预览文件。切换后，底部审核按钮必须重新绑定到新文件的当前 `artifactVersionId`。
- **保存新版本**：保存 Markdown 编辑内容，生成新的 `ProjectArtifactVersion` 并更新 current 指针。它不移动最终版，不自动通过审核，也不验收 Task。
- **通过**：打开通过确认面板。面板必须明确两个互斥选项：`通过当前已保存版本` 表示只审核 Server 当前已经保存的文件版本，即使编辑器里还有未保存修改也不纳入审核；`先保存为新版本再通过` 表示先把编辑器当前内容保存成新的文件版本，再审核通过这个新版本，相当于“保存新版本 + 通过”的组合动作。面板可以提供“同时设为最终版”勾选项；这里的最终版是当前文档/当前文件集合的 `finalVersionId`，不是整个输出包最终版，也不是 Task 完成。勾选后在同一事务中写入审核通过和最终版指针。通过不等于 Task 完成。
- **退回修改...**：打开退回面板。用户在面板里选择退回结论：`要求修改` 表示方向基本可用、基于当前版本继续改；`拒绝` 表示当前版本不可作为正式输入、需要重做或大改。面板必须要求填写意见，并选择下一步：`让原智能体修改` 会在回到讨论串时预填原智能体、当前文件版本引用和审核意见；`换一个智能体处理` 不自动指定智能体，只保留待选择的智能体位置、当前文件版本引用和审核意见。确认后写入对应审核记录和 Task delivery 退回事实，再把用户带回讨论串预填上下文。
- **查看版本历史**：展示当前文件集合的版本、来源、审核记录和最终版变更，不改变任何事实。
- **模拟冲突**：原型演示按钮，用于说明保存必须基于 Server 最新修订；真实产品中应由版本冲突检测触发。
- **打开讨论串**：从退回、处理意见或文件上下文返回原话题输入框，不自动创建新 Agent invocation；只有用户发送明确 `@智能体 + 指令 + 文件引用` 后才会创建后续执行。

### 8.1 主聊天与讨论串

主聊天区是话题入口列表，不是连续聊天流。用户在主聊天发送任何内容，都会创建一个话题；该话题的回复、Agent 请求、文件包展示、文件引用、Markdown 预览编辑和后续 `@智能体` 协作，都发生在右侧讨论串中。

聊天消息不是项目事实源。聊天只触发操作和展示操作结果；任务状态、产物版本、审核结论、最终版指针和后续 invocation 输入都必须由 Server 持久化。

`TaskStatus` 是 Server 从具名 lifecycle command 和交付事实得到的生命周期投影。客户端不得通过拖拽、下拉、快捷菜单或通用 `updateTask(status)` 把任务任意改成其他状态。用户在界面上看到的是合法动作，不是可编辑状态枚举。

### 8.2 文件引用

讨论串输入框的 `@` 选择器需要同时支持成员、智能体、文件和文件包：

- `@某个智能体` 表示下一步由哪个可见 Agent 处理。
- `@PKG-042` 这类文件包引用默认使用该包的 current projection，即包内每个成员各自的最新 Server 修订。
- `@PKG-042 final` 或“引用最终版包”显式使用 final projection，并要求所有成员都有最终版。
- `@F1`、`@F2` 这类短编号只在当前讨论串或当前文件包上下文中可见，提交给后端时必须解析为稳定的 `artifactVersionId`。
- 如果短编号存在歧义，UI 必须让用户选择，不能猜测。

整包引用当前版本时，Server 应读取包内每个产物集合的 `currentVersionId`。如果同一个包中有 3 个文件是用户手动修改过的 latest revision，2 个文件是 Agent 修订过的 latest revision，整包引用应取这 5 个文件各自最新的 Server 修订。

后续执行者不能由文件包或阶段名称写死。用户需要在讨论串中显式 `@某个智能体`，或通过等价的选择器选择目标智能体；Server 再基于频道可见性、Agent 权限和引用文件版本创建后续 invocation 或 handoff。

负责人通过执行事实产生。任务页不直接选择负责人，也不提供首版主入口来创建待办任务。只有用户在讨论串发送 `@智能体 + 文件引用 + 指令` 后，Server 才创建 Task/Invocation，任务负责人或当前责任焦点才投影为该智能体。

### 8.3 预览编辑与 Server 修订

Markdown 预览浮窗既可以只读预览，也可以直接编辑，也是首版逐文件审核的主工作面。保存时不覆盖旧文件，而是为对应 `ProjectArtifactCollection` 生成新的 `ProjectArtifactVersion`，并更新该集合的 `currentVersionId`。

保存必须基于 Server 最新修订。如果用户打开浮窗后，Server 已经产生了更新版本，保存时应提示冲突，让用户查看最新版后再保存为新版本。后续 Agent 和其他用户都只能基于 Server 当前修订或最终版指针继续，不能基于本地旧草稿或聊天里的旧文本继续。

人工保存的新 Markdown 版本默认成为 current，并可被后续 Agent 使用；但它不会自动继承或移动 `finalVersionId`。如果原版本是 final，保存后的新版本应显示为“当前版 · 人工修改 · 未设 final”，用户需要在通过确认面板中显式勾选“同时设为最终版”，或在已通过版本上单独执行“设为最终版”。

手动编辑保存后，讨论串应自动留一条轻量事件，例如“derrick 手动修改了 F1，第1集剧本.md -> v5”，并提供预览、引用和查看历史入口。不要把 Markdown 全文重新贴到聊天中。

Markdown 与图片都进入同一套 current / final / review / reference 模型。Markdown 首版支持内置预览编辑；图片支持预览、引用、审核、设 final，首版不做图片内置编辑。PDF 或其他文件暂不作为首版重点，但模型不刻意排斥。

预览浮窗应展示本次输出包的文件列表、每个文件的当前版本、审核状态和最终版状态。切换文件时，右侧审核动作必须重新绑定到新预览的 `artifactVersionId`。如果用户有未保存编辑后点击“通过”，系统不能静默把审核结论落到编辑前的旧版本；必须在通过确认面板中明确让用户选择审核当前已保存版本，或先保存为新版本再审核新版本。若同时勾选“设为最终版”，落库顺序是保存新版本、写入通过审核、移动最终版指针；仍不自动验收 Task。

Server 修订与本地或 Agent 工作区文件的同步策略待文件同步架构统一确认。无论底层是否自动同步，交互和后续 Agent 输入都必须以最新 Server revision 为准；本地文件只能是同步副本或执行副本，不能替代 Server 事实源。

### 8.4 审核动作

审核按钮只处理当前文件版本，不自动决定后续交给哪个智能体，也不直接完成 Task。当前文件版本必须来自明确的用户上下文，例如预览/编辑浮窗当前文件、交付文件列表中被打开的文件或文件版本历史；UI 不能在没有明确审核对象时展示一组泛化的“通过/要求修改/拒绝”按钮。

- **通过审核**：为当前文件版本写入通过的 `ArtifactReview`，并把对应版本标记为已通过或可被后续引用。通过审核不等于最终版，也不等于 Task 完成。
- **要求修改**：打开退回面板，要求用户填写修改意见并选择下一步处理方式。确认后写入要求修改的 `ArtifactReview` 和审核意见，当前版本保留为被要求修改的版本；如果这是当前 delivery 的退回动作，还必须通过具名 command 退回 Task delivery，并产生新的 revision/attempt，再把用户带回讨论串预填原智能体或新智能体、文件版本、审核意见和任务上下文。
- **拒绝此版本**：打开退回面板，要求用户填写拒绝原因和重做要求，并选择下一步处理方式。确认后写入拒绝的 `ArtifactReview` 和拒绝原因，该版本不能作为后续默认输入；如果这是当前 delivery 的退回动作，还必须退回 Task delivery，再把用户带回讨论串预填原智能体或新智能体、文件版本、拒绝原因和任务上下文。拒绝不是流程结束，而是带着原因发起重做或重新处理。
- **批量审核文件**：在输出包卡片、文件页版本列表或预览浮窗左侧成员列表中一次性选择多个文件版本，落库为多条文件版本审核记录。批量动作不能产生一条 package-level review 来覆盖所有文件。

这些动作必须保留审核人、审核时间、审核意见、审核对象和依据文件版本。

退回面板至少包含：

- 退回结论：要求修改或拒绝。
- 审核意见：必填；用于告诉智能体具体怎么改、为什么不可用或哪里需要重做。
- 下一步处理方式：默认让原智能体修改，也可以换一个智能体处理。选择让原智能体修改时，讨论串输入框应预填 `@原智能体 + 当前文件版本引用 + 审核意见 + 原任务上下文`；选择换一个智能体处理时，不自动填具体智能体，应保留待选择的智能体位置或选择器，同时带入当前文件版本引用、审核意见和原任务上下文。
- 确认后行为：写入审核和交付退回事实，回到讨论串并预填上下文；系统不自动发送，不自动重跑智能体。只有用户在讨论串确认发送后，Server 才创建新的 invocation/claim。

审核人可以在任务页预设，也可以为空。预设审核人表示期望或筛选条件，不等于最终审核归属。最终审核归属必须以实际执行审核动作的人为准：即使预设审核人是 A，如果有权限的成员 B 点击了通过、要求修改或拒绝，`ArtifactReview.actorId` 也必须记录为 B。

审核动作和最终化动作必须以 Server 返回的 `availableActions` 为准。UI 可显示“建议审核人：A”或“审核人：未指定”，但不能把建议审核人、Task assignee 或频道成员身份当作审核权限。

### 8.5 Task 交付验收

Task 交付验收是独立于文件审核和最终版设置的动作。

Task 交付验收人可以和文件审核人是同一个人，首版也可以默认如此；但这是两个可审计事实的同人持有，不是同一个权限。UI 不需要让用户维护两套复杂角色，只需要根据 Server 返回的动作分别展示文件级按钮和任务级按钮。

- Agent 交付文件包后，当前 Task delivery 进入 `in_review`，页面显示为“等待审核交付”。
- `in_review` 中必须展示文件审核覆盖和交付验收门槛。
- 文件全部通过后，用户仍需执行“验收交付”才可让 Task 进入 `done`。
- 如果产品提供“全部通过并验收交付”，该组合命令必须在同一事务中写入多条文件版本审核记录和一条 Task delivery acceptance。
- 只要任何必需成员版本处于待审核、要求修改或已拒绝状态，Task 不允许验收交付。
- `done`、`cancelled` 和 `closed` 都是终态，不能回退到非终态；继续工作应创建 follow-up、continuation 或 replacement task。

UI 文案应使用“验收本次交付”，不要直接显示 `Task delivery acceptance`。当文件未全部通过时，禁用态提示应写成“还有文件未通过审核：第1集剧本待审核，分镜提示词需要修改”，不要写“文件审核覆盖未满足”。

### 8.6 最终版

“设为最终版”是独立的版本选择动作，写入 `ProjectArtifactCollection.finalVersionId`。它不应该只通过文件名、标签、目录或聊天文字表达。

通常只有已通过版本才能设为最终版。如果产品允许当前版本未通过时直接设最终版，UI 不应再增加一个常驻主按钮，而应在“通过”确认面板里提供“同时设为最终版”勾选项，并在一次事务里同时写入审核通过记录和 final 指针。

同一产物集合同时只能有一个最终版。新最终版产生时，旧最终版不删除，应保留历史并标记为被取代或回到已通过状态。

“通过并设为最终版”和“通过并验收交付”不要默认合成一个常驻主按钮。通过确认面板或批量确认面板可以允许用户勾选“同时设为最终版”“同时设为各文件最终版”或“文件全部通过后验收交付”，但 UI 必须清楚区分文件审核、最终版和 Task 验收三类事实。

### 8.7 继续协作

“回到讨论串继续”不写入最终版或任务完成状态。退回修改也不自动重跑 Agent。它只把用户定位到当前话题输入框，并把退回结论、当前文件版本引用、审核意见和原任务上下文带入输入框。若退回面板选择“让原智能体修改”，输入框预填原智能体；若选择“换一个智能体处理”，输入框不自动指定具体智能体，让用户重新选择。用户通过 `@智能体 + @文件/文件包 + 审核意见` 指定下一步，例如：

```text
@某个智能体 请基于 @PKG-042 或 @F1 @F2 继续处理。
```

后端创建后续 invocation 或 handoff 时，必须校验目标 Agent 可见性、频道权限、阶段依赖和引用文件版本。执行输入由 Server 根据稳定引用组装，不从聊天长文本中复制文件内容。

### 8.8 文件页字段

文件页按逻辑产物集合组织，不按聊天附件堆叠。字段含义如下：

- **名称**：用户可读文件名，以及内部产物集合标识。
- **类型 / 阶段**：项目语义类型和所属阶段，例如 `script`、`prompt`、`image`。
- **来源**：产物来自哪个 Agent、哪次 Workspace Run、哪条消息、是否有人类手动修改。
- **当前版**：该集合的 `currentVersionId`，代表最新 Server 修订。
- **最终版**：该集合的 `finalVersionId`，代表人工确认的最终版指针。
- **审核**：当前版本的审核状态，例如待审核、已通过、要求修改、已拒绝或可用。
- **动作**：预览/审核、编辑、引用、查看历史、基于此修改等入口。通过审核、要求修改、拒绝、设 final 等逐文件动作在预览/编辑浮窗内执行，并最终落回 Server 事实模型。

文件页左侧集合列表的展示规则：

- **产物集合**：同一逻辑交付物的版本容器，例如 `character.sheet`。
- **输出包**：一次 Agent 交付的一组文件，例如 `PKG-042`。输出包可以跨多个产物集合。
- **current projection**：输出包当前投影，读取包内每个产物集合当前的 `currentVersionId`。
- **短编号**：`F1/F2/IMG` 只用于当前消息或当前讨论串识别，不能作为后端长期身份。
- **批量审核**：输出包提供的便捷操作，只对包内文件版本逐条写入审核记录，不创建包级审核版本；不同结论应进入预览浮窗逐项处理。

## 9. 权限与安全

- 只有能访问频道的人才能看到项目阶段和项目文件。
- 审核、要求修改、拒绝版本、设置最终版和验收交付都必须由 Server 依据当前操作者、项目负责人、阶段审核者、Team 角色和当前 delivery/revision 计算 `availableActions`；客户端只展示这些动作，不能自行放权。
- 文件版本审核 authority 与 Task 交付验收 authority 必须分开计算和审计；首版默认配置可以让同一人同时具备两类动作，但不能把一类动作的可见性当成另一类动作的授权。
- 实际操作者必须写入审核记录、最终版事件或交付验收事实。
- Agent 可以产出文件和建议下一步，但不能直接批准审核、设最终版或改项目阶段事实。
- 所有跨阶段交接都必须校验目标 Agent 可见性、频道权限和阶段依赖。
- 被归档或删除的频道不能继续产生项目变更。

## 10. 验收标准

实现完成后，至少应满足这些场景。

### 场景 1：项目负责人看阶段进度

项目负责人进入频道任务页，可以看到剧本、服装、分镜、审核等已有执行事实对应的阶段，以及每个阶段的当前责任焦点、状态、建议审核人、实际审核人、阻塞点和交付物数量。首版任务列表不展示常驻待办列，也不提供“新建任务”主入口。

### 场景 2：Agent 产出后进入审核

编剧 Agent 在剧本阶段产出多个文件后，系统能把这些文件归档为输出包成员和项目产物版本，并让当前 Task delivery 进入“等待审核交付”。文件页输出包概览应展示每个成员版本的审核状态和最终版状态；点击待审文件后，预览/编辑浮窗展示内容和当前文件审核动作。

### 场景 3：多文件中选择指定文件修改

一条 Agent 消息包含 10 个文件时，用户可以明确选择第 3 个文件发起修改。发送给 Agent 的请求必须引用稳定文件版本，而不是只写“第 3 个”。

### 场景 4：最终版可追溯

用户把某个已通过版本设为最终版后，文件库能显示最终版；后续能追溯它来自哪条消息、哪次运行、哪个阶段和哪个 Agent。

### 场景 5：文件审核和交付验收后交给下一阶段

剧本阶段的必需文件版本已通过审核且当前 delivery 已被验收后，服装或分镜 Agent 能按阶段输入规则拿到已通过或最终版剧本作为输入继续工作。

### 场景 6：审核拒绝后显式继续生成

审核者拒绝某个版本或要求修改并提出意见后，系统保留文件版本审核记录和 Task delivery 退回事实。系统不自动重跑 Agent，但能在讨论串中预填被退回版本、审核意见和任务上下文，让用户显式选择原 Agent 或其他 Agent 发起重新生成或修改请求。

### 场景 7：任务状态不可手动回退

用户不能通过看板拖拽、任务详情按钮或列表下拉把 `done`、`cancelled` 或 `closed` 改回 `in_progress`。需要继续工作时，系统应引导创建 follow-up、continuation 或 replacement task，并保留原 Task 和文件版本 lineage。

### 场景 8：批量审核不创建包级审核

用户对输出包执行“全部通过”或“全部要求修改”时，系统为包内目标成员版本分别写入审核记录，并在 UI 中显示聚合结果。系统不得只创建一条 package-level review 来覆盖所有文件。

## 11. 暂不解决

这些能力不放进首版：

- 跨频道项目。
- 项目模板市场。
- 甘特图、日历排期和资源负载。
- 文件内容 diff。
- 多最终版分支管理。
- 完整普通人工任务执行/审核工作流。
- 面向外部客户的交付门户。

首版先把“项目阶段、审核、文件版本、最终版、多文件选择、Agent 交接输入”做对。
